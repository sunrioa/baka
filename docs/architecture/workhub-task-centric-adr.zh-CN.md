# ADR 草稿：WorkHub 以任务为中心的精简设计

- 状态：已确认；本次为实施前规则澄清，尚未修改程序
- 修订日期：2026-10-19（补齐执行契约，保留 AI 自主决策）
- 适用仓库：sunrioa/baka
- 代码基准：`a7f6925`（2026-10-18）。本文所有"现状"描述均来自源码，不依据现有文档
- 相关讨论：apache/maka#5745、sunrioa/baka#8

---

## 1. 背景

WorkHub 的目标是让用户只通过一个对话推进工作，不需要自己管理 Session。apache/maka#5745 已形成"做减法"的共识：去掉预路由，由协调 Agent 直接用工具决策；去掉纠正事务；去掉跨会话问题转发；目标校验不再绑定整个候选快照。

baka 在此基础上实现了任务身份（workId）、任务视图、多段 Session 接力（fresh continuation）等能力，但同时保留了 #5745 计划删除的机制，并新增了任务级授权、依赖等待、跨会话问答等协议。

源码核对发现的主要问题：

| 问题 | 位置 |
|---|---|
| `stop`、`correct`、`tasks` 的工具描述声称 Host 会检查用户意图，代码中没有这项检查 | `workhub-tool-schema.ts:239,248`；`workhub-control.ts:284`；gate 只检查 `userText` 非空（`workhub-coordination-action-gate.ts:350`） |
| 结果通知触发的协调轮次里，"用户原文"实际是当初派活时的原文，并非用户新指令 | `root-turn-coordinator.ts:2147-2159` |
| 候选集 ID 是对最多 32 个候选整体做摘要；每次委派都会更新目标的 `lastMessageAt`，导致候选集过期 | `workhub-coordination-action-gate.ts:1270-1286,1384` |
| 换窗时使用**当前**的 WorkHub 默认值（模型、执行器、权限），不是任务原来的设置 | `workhub-runtime.ts:163-179`；`execution-composition.ts:2686-2708` |
| 新任务的模型、执行器、思考级别默认值只存在进程内存，重启即丢失 | `workhub-new-work-defaults.ts:27-36` |
| 换窗交接只有一段固定说明加原始目标前 512 字节，没有简报 | `execution-composition.ts:2406-2417` |
| 复用还是换窗由模型决定；现有上下文信息主要出现在 `works` 结果里，尚未明确区分观测用量、缓存估计与压缩风险 | `workhub-work-index.ts:115-139` |
| 普通工具权限的审批在 WorkHub 里无法处理 | `workhub-task-inbox.tsx:119-123` |
| 选择表单没有"新建任务"选项 | `workhub-coordination-coordinator.ts:708-750` |
| 界面多处暴露 Session 和原始 ID（任务卡片、任务视图标签、派发卡片） | `workhub-task-overview.tsx:74-98`；`workhub-task-view.tsx:74` |
| `status`、`WorkHubInspect` 只能访问最近 32 个候选会话 | `workhub-runtime.ts:102-105`；`workhub-inspection-tool.ts:132` |
| 安全边界恢复默认允许交互调用、禁止自动调用；工具合并不能默认为自动调用开放此能力 | `safe-boundary-resume-policy.ts:28-36` |

## 2. 目标与范围

**目标**：在 WorkHub 里，用户只面对"一个对话 + 一份任务列表"。协调模型负责分发请求，并判断复用已有 Session、新建 Session，还是换窗接力。

**范围**：

- 只在 WorkHub 内弱化 Session 和项目概念。Maka 其他界面（项目、Session 列表、设置）保持不变。
- 不批量重写历史。已有持久数据保持可读；已删除协议不再驱动新动作，但升级时未完成的操作需要按第 6 节幂等收尾，不能只忽略。
- WorkHub 创建的会话底层仍是普通 Session，在主界面仍可打开。

**非目标**：Project 层；跨 Host、跨设备；子代理统一预算；Windows 新沙箱后端。

**精简原则**：AI 决定任务关联及是否复用、换窗；Host 只保证目标归属、执行身份、权限、排队和幂等正确。不新增意图识别层、强制换窗阈值、独立交接摘要协议、全文件系统首次写入拦截或新的通用恢复框架。

## 3. 决策

### 3.1 概念模型

```
任务（workId）  用户关注的单位：标题、状态、设置快照、简报
   └─ 执行段（Session）  第 1 段、第 2 段……，用户在 WorkHub 里看不到 Session 这个词
```

- 一个任务可以由多段 Session 接力完成；换窗不改变 `workId`。
- `reuse`：继续使用当前 Session，仍可触发现有压缩；`fresh`：用新 Session 接续同一任务，不复制旧 Session 的全量上下文。新建独立任务使用 `start`，不是 `fresh`。
- 工作目录是任务的内部属性，不暴露"项目"概念。

### 3.2 用户界面（仅 WorkHub 内）

| 界面 | 内容 |
|---|---|
| 统一对话 | 一个输入框：提问、下达任务、追问、改要求、停止 |
| 设置 | WorkHub 模型（协调者与新任务共用，持久保存）、新任务权限（ask / bypass）、并发数（1～8，未配置时默认 3；升级保留已有设置） |
| 任务列表 | 任务标题（独立于会话名）、状态（见 3.2.1）、搜索；不显示原始 ID |
| 待你处理 | 列出需要处理的事项，点击跳转到对应任务 |
| 任务视图 | 各段连续显示（标为"第 N 段"）；直接对任务输入；就地处理**所有类型**的审批；停止按钮 |

主侧栏中，WorkHub 创建的会话折叠为一组。

#### 3.2.1 任务状态

不设"待验收"等需要用户手动确认的状态。任务只有以下 5 种状态，全部由系统自动得出：

| 状态 | 含义 | 合并自现有状态 |
|---|---|---|
| 排队中 | 已受理，还没开始执行 | `queued`、`waiting_resource` |
| 执行中 | 正在执行 | `running`、`stopping` |
| 待你处理 | 有问题或审批等你回答 | `waiting_for_user` |
| 已结束 | 这一轮执行正常结束 | `pending_acceptance`（现状只是改名，没有验收操作） |
| 失败 / 已停止 | 出错，或被停止 | `failed`、`unavailable`；`cancelled`、`stopped` |

`waiting_for_dependency` 随依赖等待（E）一起删除。

"执行结束"不等于"目标已达成"。这一点由结果内容说明（允许时附 worker 状态块，见 3.7.2），而不是增加验收状态。已结束的任务仍可被 `find` 找到并 `continue`，只是排序靠后。

### 3.3 协调模型的任务工具

| 工具 | 作用 | 取代 |
|---|---|---|
| `find` | 查找任务和可派活的手动会话，附带观测信息与成本估计（见 3.4）。规模与排序见 3.10 | `works`、`candidates`、`projects` |
| `start` | 新建独立任务：标题、内容、可选位置提示 | `create_new` |
| `continue` | 继续同一任务，可选 `reuse` / `fresh`；不同状态的行为见下表 | `continue_work`、`delegate_existing`、`correct`、`resume` 的入口，恢复策略不因此开放 |
| `ask` | 有歧义时让用户选择，任务选择项包含"新建任务" | `select_and_delegate` |
| `stop` | 停止执行或取消尚未执行的排队任务（确认规则见 3.9） | `stop` |
| `read` | 按授权读取状态、最新回复、历史、完整结果，范围见 3.3.2 | `status`、`WorkHubInspect`、`WorkHubResult read`、`WorkHubEvidence read/list` |

保留：界面控制、浏览器、附件读取、AskUserQuestion。工具描述必须与代码一致，不得声称 Host 检查用户意图。

#### 3.3.1 统一输入的执行契约

`continue` 与任务视图直接输入共用同一个 Host 命令；侧栏发送默认是对当前任务的普通补充，不隐式换窗。

| 目标任务状态 | 普通输入 / `reuse` | `fresh` |
|---|---|---|
| 排队中 | 追加到原受理内容，保留排队位置、并发与同目录串行规则 | 第一版不接受；返回"任务尚在排队"，不创建新段、不替换原受理 |
| 执行中 | 使用现有 Steering，在下一次可消费输入的模型边界进入本轮；不打断正在执行的工具，不另开一轮 | 第一版不接受立即换段；返回"任务仍在执行"，由模型之后重新判断，不建立延迟换窗队列 |
| 待你处理 | 普通补充不等于审批通过；问题与审批仍通过原交互请求回答 | 有未决交互时不接受，不用换窗绕过审批 |
| 正在停止或恢复中 | 明确返回暂不可受理，不能声称纠正已进入执行 | 等旧执行及其资源归属收尾后才可受理 |
| 已结束、失败或已停止 | 在原 Session 创建普通新一轮，仍经现有队列准入 | 无旧排队、活动执行或未决交互后新建执行段，保持同一任务并走现有队列 |

说明：

- "本轮读到"指在可消费消息的边界进入同一轮，不承诺正在运行的 Bash 等工具会即时读取消息或改变行为；内容由 Agent 理解。
- 工具命名合并不等于自动恢复旧执行。安全边界恢复继续使用现有策略与校验（`safe-boundary-resume-policy.ts`）；普通续作不自动重放被中断的工具。
- 回执区分排队追加、Steering 已受理、新一轮已受理和未受理；受理不等于 Agent 已消费，更不等于要求已执行。
- 任务视图输入绑定当前任务；WorkHub 总输入按总对话及用户语义选择任务，右栏预览选择不隐式改变派发目标。

#### 3.3.2 历史读取范围

- **同一任务的旧段**：新段可分页按需读取原始要求、后续纠正、助手可见回复、工具调用参数与可见输出；按任务执行血缘筛选，不把整个旧 Session 自动归入该任务。
- **其他任务**：保留现有授权下的结果、证据读取能力；本次不把同任务完整历史权限自动扩展为任意任务或任意 Session 的完整转录权限。
- **手动 Session 接入**：接入前没有任务归属证明的内容，不自动算作新任务历史；已有普通会话查看能力不变。需要这些内容时走既有授权读取路径，不伪造归属。
- 继续保留隐藏内容过滤、附件与工具产物的原有访问规则。缺失、已删除、归档不可读或执行器不支持时，明确返回限制，不能静默当作空历史。
- 新段只携带有界的任务说明与历史入口（见 3.7），不复制全部上下文；简报不是原始历史的替代品。ai-sdk 与 executor 的可用能力需分别验证，不支持时不得宣称换窗续作已完整支持。

### 3.4 复用还是换窗

- **由协调模型自主决定** `reuse` 或 `fresh`。Host 不因闲置时长、上下文 token 数、占用比例、预测压缩或缓存可能已冷而强制换窗，也不设置统一数值阈值。
- 上下文窗口沿用当前模型、连接与 Maka 的有效配置，不写死 900k、1M 或固定占比。选择复用后，仍使用现有压缩机制；本 ADR 不修改其触发算法。
- Host 在 `find` / `read` 与任务选择项中提供以下信息，明确标注来源及"已观测 / 估计 / 未知"：
  - 最近一次供应商报告的输入、输出与缓存用量，以及当前有效窗口；磁盘历史累计长度不作为当前请求上下文用量。
  - 最近模型请求时间；会话活动时间如单独提供，不能冒充缓存访问时间。TTL 仅用于提示"可能已冷"，无法确认命中。
  - 按现有运行时信号估计的压缩风险；新追加输入尚未计量、窗口或用量缺失时，标为未知，不能承诺下一次一定压缩或一定不压缩。
  - 当前连接价格可确认时，估算复用首请求、压缩及换窗后按需读取的成本，写明假设；未知价格或未来重读量不补造数字。第一版不增加独立成本预测模型。
- 若有推荐，只是提示，不覆盖模型选择；忙碌时换窗不可执行等运行状态限制按 3.3.1 返回，不转换成语义路由规则。
- 每次决策关联现有操作记录与请求用量，记录选择及可观测结果。价格换算是估算费用；仅供应商账单可确认实际计费。

#### 3.4.1 压缩的实际行为与成本边界

源码基准 `a7f6925`：

- 主动压缩的一项触发条件是"最近有效请求的实际输入 + 输出 + 按上一回复推算的回复预留空间 ≥ 当前有效窗口"（`ai-sdk-compaction.ts:880-934`），也有供应商上下文溢出后的恢复路径。新增外部输入未必已被这份基线计入。
- 压缩折叠安全完成的历史前缀，构造"压缩块 + 当前轮原文锚点 + 未折叠尾部"的模型请求投影；原始持久转录并未因此删除（`ai-sdk-compaction.ts:973`）。
- 已有检查点时，总结器可用"上一份摘要 + 新折叠事件"增量更新，不是每次重读全部原始历史（`history-compact-summarizer.ts:115-140`）。
- 默认总结输出上限为 8,000 token，不是每次固定输出或仅剩 8,000 token。截断、修复或溢出回退也可能增加请求次数。
- 总结指令放在尾部只是复用前缀缓存的尝试。主循环与总结请求的系统提示、工具定义等并不相同，实际缓存命中需查看供应商用量，不能仅凭注释保证。

因此：

1. 压缩减少当前模型请求携带的原文，不等于删除历史，也不等价于 Host 拼装的任务简报；两者保留的信息与重新取证成本可能不同。
2. 复用与换窗的总成本都包含之后完成同一请求所需的读取、工具调用、输出及可能的压缩；仅比较换窗起步 token 与旧历史总长不足以下结论。
3. 不保留原稿中缺少实测依据的固定冷热费用表，也不据此认定"缓存可能已冷时换窗几乎总是更省、更快"。窗口取当前有效配置、价格按适用连接核实，实测结果用于给 AI 提供信息，不形成强制换窗开关（见 8.1）。

### 3.5 任务设置快照

- 任务创建时记录权限、模型 / 连接、执行器及其模型、思考级别、工作目录等有效设置。修改 WorkHub 的默认值只影响新任务，不追溯覆盖已有任务。
- **WorkHub 新建任务**：初始快照取创建时的 WorkHub 默认值；**手动 Session 接入**：初始快照取该 Session 当时的有效持久配置，不改写其配置、不做按轮覆盖。
- **用户后续明确修改当前段设置时，尊重该修改**。复用继续读现有 Session 配置；换窗前读取当前段有效的持久设置，作为新段的继承依据并记入阶段记录，不能静默恢复创建时的旧权限或模型。没有明确修改时沿用既有任务设置。
- 单次审批、`rememberForTurn` 或临时沙箱许可不作为持久任务配置，不跨轮、跨段扩散。配置不可用、连接失效或执行器缺失时明确报错或请求用户处理，不静默提高权限或改用 WorkHub 当前默认模型。
- 工作目录身份与资源占用继续使用现有规范化和准入校验；任务文本里出现一个文件路径，不等于用户修改了任务工作目录。
- 现状：运行时从会话头读取权限模式（`runtime-kernel.ts:2695,3167`；`agent-run.ts:1449`）。本 ADR 不引入按轮权限覆盖；手动会话为 ask 时，审批仍按该会话规则处理。

### 3.6 工作目录解析

按顺序：

1. 续作：继承原任务当前有效目录；明确修改按现有配置与目录准入规则处理；
2. 请求中明确指定任务工作目录：使用该目录，不把普通待访问文件路径误当工作目录；
3. 匹配历史任务用过的目录（底层复用项目注册表，不暴露给用户）；
4. 不涉及目录的任务：Host 私有临时目录；
5. 仍有歧义：用 `ask` 询问。

**权限边界**：工作目录不是文件系统访问边界，脚本可能写入目录之外。本次沿用现有工具权限、目录准入与沙箱审批，不承诺拦截"任何工具对任意新目录的首次实际写入"，也不新增通用拦截机制或独立的工作目录确认规则。只读 / 写入及 ask / bypass 的行为仍由原权限系统决定；历史任务用过或注册过某目录不自动授予额外访问权限。

### 3.7 任务简报

**目的**：换窗时，不全量复制旧对话；按需临时拼装有界任务说明与历史入口，让新段知道"要做什么、用户说过什么、去哪里查证"。此处沿用"简报"名称，但不新增独立交接摘要、交接任务或模型总结调用。

**原则**：简报不单独存储，在需要时由 Host 从已有记录**临时拼装**，不额外调用模型；任务与阶段事实按 3.10 持久记录。允许时由 worker 附加状态块到原转录，不新增汇报工具或后台总结流程。

#### 3.7.1 来源

| 简报内容 | 来源 | 可信度 |
|---|---|---|
| 目标 | 任务最初的用户请求（派活记录中的 `userText`） | 用户原话 |
| 后续要求与纠正 | 发给该任务的全部用户输入：协调对话里的 `continue` 文本、任务视图里的直接输入，按时间排序 | 用户原话 |
| 最新进展 | 最近一段最后一个状态块（见 3.7.2） | worker 自述，未经验证 |
| 待办 | 最近一段的 session-todo（`content` + `status`），仅在可确认属于本任务时使用 | worker 记录 |
| 可确认的文件操作 | 本任务中有成功结果佐证的 Write/Edit 等文件操作路径，去重；失败或结果未知时分别标注 | 不是完整改动清单，不把调用尝试当成功 |
| 历史位置 | 固定提示：需要细节时用 `read(taskId, view=history)` 读取旧段 | — |

#### 3.7.2 worker 状态块

WorkHub 派出的任务，在不冲突于用户输出要求时，可在该轮最后附加：

```
<task-status>
完成：……
未完成 / 下一步：……
已验证：……（例如"测试 xx 通过"或"未运行测试"）
需要用户决定：……（没有则省略）
</task-status>
```

- 有状态块时预计增加约 100～200 个输出 token，以实际用量为准。
- 用户要求纯 JSON、仅一行等严格输出时优先遵守用户格式，不强制状态块，也不另开模型调用补写。
- Host 只取本任务最近一个有效状态块；缺失时可引用最后助手回复前 800 字符并标为"回复摘录，非完整进展"，不足则标未知。不把工具输出或历史引用中的同名标签当作 worker 新报告。
- 状态块是未经验证的 worker 自述，不能覆盖用户后来纠正或作为自动验收依据；"完成"一行可用于 `find` 的自述摘要。

#### 3.7.3 拼装时机与格式

在以下时机拼装：

- `continue(…, fresh)` 开启新的一段时，作为该段第一条消息的一部分；
- 任务视图顶部的"任务概况"（只读展示）。

格式示例：

```
任务简报（Host 根据记录生成，第 3 段开始）
目标：给登录接口补完整的参数校验，并补限流测试。
用户后续要求（最新在后）：
- 10/12 14:03  别改样式，只修逻辑
- 10/13 09:20  限流阈值用 10 次/分钟
最新进展（第 2 段结束时 worker 自述，未经验证）：
  完成：参数校验与单元测试
  未完成：限流测试
  已验证：单元测试 23 项通过；未运行集成测试
待办：[x] 参数校验  [ ] 限流测试
可确认的文件操作：src/auth/login.ts, src/auth/login.test.ts（非完整改动清单）
需要更早的细节时，用 read(taskId, view=history) 读取。
```

#### 3.7.4 大小与截断

- 简报上限约 3k token。
- 超限时的保留优先级：目标 > 最新的用户要求与纠正 > 最新进展 > 待办 > 文件列表 > 较早的用户要求。被截断的部分标注"已省略 N 条，可用 read 查看"。
- 目标超过 1,500 字符时截断并标注。
- 原始要求与纠正完整保留在历史读取入口；简报注明来源与省略，不宣称已包含全部约束。明确取代旧要求的后续纠正优先；存在歧义时由 Agent 读原文或询问，不由 Host 做语义改写。

#### 3.7.5 缺失信息与已有压缩摘要

- 拼装与缺失信息处理均不新增模型调用；没有状态块、todo 或文件操作时直接标未知，提供历史入口，由 Agent 按需读取。
- 已有压缩检查点只有在可确认属于本任务时才可引用，注明它是历史摘要且可能省略细节；无法确认范围时只提供定位，不把共享 Session 的总结自动当本任务事实。
- 不因为旧段很长或简报字段为空就自动读完整历史补写交接总结；原 Session 的压缩仍按既有运行时机制执行。

#### 3.7.6 成本

| 项目 | 成本 |
|---|---|
| 拼装 | 0 次模型调用 |
| 状态块 | 有输出时计实际 token；严格格式场景允许缺失 |
| 简报注入 | 第一轮增加实际说明长度，后续是否缓存及如何计费由供应商决定，不保证命中 |
| 按需读取 | 计入历史页、工具输出等进入后续模型请求的实际输入及输出成本 |

#### 3.7.7 用户可见性

第一版只读展示在任务视图顶部，不提供编辑。用户要修改方向时直接对任务说话，这些话会作为"后续要求"自动进入下一次简报。

### 3.8 审批

- 所有审批（工具权限、沙箱越界、客户端能力）都在任务视图里，对原请求处理。
- 工具权限审批提供"允许一次""本轮内都允许""拒绝"，直接使用现有回答字段 `decision: allow | deny` 与 `rememberForTurn`（`interaction.ts:195-197`），不新增权限范围。
- 沙箱越界、客户端能力请求使用其现有的原始审批选项，不再提供任务级授权。
- "待你处理"只列出事项并链接到任务。
- 审批不经过协调模型。

### 3.9 Gate 与 stop 确认

Gate 不做自然语言意图判断，也不绑定整个候选列表；保留以下执行正确性检查，沿用现有准入、血缘和幂等能力：

- 目标任务及段确实存在，Session 未归档、不是协调会话，且符合现有可派发资格；手动会话按原资格接入，不借此放开其他受限会话。
- 操作对应当前任务、阶段及具体执行；提交前在现有锁 / 准入边界复核，旧阶段的消息不能误送到新阶段，不能 Steering 同 Session 内另一任务的执行。
- `actionId` 与动作、内容和目标执行绑定；同一请求重放返回原结果，不因当前执行变化而改停新一轮。冲突明确返回，不能换目标后偷偷重试。
- 仍检查现有权限、未决交互、FIFO、并发名额与同目录串行。新段不能与旧段并行占用同一任务的执行权。
- `stop` 可取消本任务尚未开始的排队受理，也可停止其拥有的活动执行；已结束则返回已结束。归属不可证明时不报告停止成功，不影响其他任务。

`stop` 确认规则：

| 情况 | 处理 |
|---|---|
| 本轮由用户消息开始，只涉及一个不同目标任务 | 直接停止或取消排队 |
| 本轮由结果通知等自动事件触发 | 沿现有交互请求由用户确认 |
| 已知要停止多个任务 | 执行前确认目标集合 |
| 同一协调轮已直接停止一个任务，又请求停止另一个 | 第二个及新增目标需确认；相同动作重放不重复计数 |
| 用户在任务视图点击停止按钮 | 直接操作该任务当前受理 / 执行 |

权限为 bypass 时，上述确认规则不变；确认回答仍绑定原请求和目标，不能顺带授权后来的新执行。

**消息来源**：

- Host 从现有准入 / 执行记录区分"用户新消息"与"结果通知"，不信任模型自报的来源。
- 自动通知携带的原始派活文字只是历史背景，不当成用户再次发出的指令。协调模型据此汇报或推进已有明确授权的工作，不因旧文字再次 `start`、`continue` 或 `stop`。没有续作依据时汇报或询问；Host 不另加意图识别器。

### 3.10 任务索引与规模

由模型控制 Session 后，Session 数量会持续增长。设计原则：**模型搜索的对象是任务，不是 Session**。一个任务换窗多次会有多个 Session，但对模型仍是一个任务。持续增长的是任务数量，需要索引支撑。

现状（`a7f6925`）：

- `candidates` 只取最近更新的 32 个会话（`workhub-coordination-action-gate.ts:1273-1276`），之外的会话无法被派活、查状态或读取。
- `works` 倒序扫描协调对话中的派活记录，每页 64 条 / 256KB，用子串匹配原始请求、任务内容与会话名（`workhub-work-index.ts:78-110`）。历史越长，找旧任务需要翻的页越多；同一任务可能跨页重复；游标在 Host 重启后失效。

决策：

1. **任务索引表**：在现有 `runtime.sqlite` 中增加一张表，每个任务一行：标题、状态、最后活动时间、工作目录、原始请求摘要、简报摘要、各段 Session。全文检索覆盖标题、原始要求与纠正、简报等可搜索文本；展示摘要不能代替全文检索内容。该表是**可重建的投影**，不是唯一任务记录：
   - 任务身份、初始标题、设置依据、各段 Session 与阶段绑定，必须先落在现有持久派活 / 阶段记录里；已有字段直接复用，仅补缺失字段，不新建并行的任务权威库。
   - 状态和待处理事项从派活、执行及交互记录共同投影；不能只从派活成功推断正在执行或已结束。
   - 先持久提交权威事实，再幂等更新索引；更新失败可从既有记录补建。重建后任务、阶段关联与有效配置不丢失，简报仍临时拼装，不单独保存全文。
   - 旧数据没有创建时设置的，标明缺失；需要续作时可引用当前段有效配置并注明来源，不冒充原始快照，也不以默认 bypass 补缺失。
2. **`find` 返回规则**：
   - 不带关键词：先列未结束任务，再按最近活动列已结束任务，每页 10 条。**不设时间截止**，通过分页游标可以一直翻到最早的任务，任何任务都不会因为太旧而找不到。
   - 带关键词：在全部任务中搜索，流程见 3.10.1。
   - 可按工作目录过滤。
   - 单页按任务去重；无索引变动时跨页不重复。游标绑定查询、目录、匹配方式与排序位置，保持 Host 重启后可续读；查询或索引格式不兼容时明确提示重新查询。实时更新可能改变排序，分页是实时集合的尽力遍历，不承诺冻结快照；模型按 taskId 识别重复，重新查询可见最新结果，不建立版本化分页或完整结果缓存。
   - **只返回一页**：Host 每次查询索引只取当前这一页，其余结果留在数据库中，不进入模型上下文，Host 也不在内存中缓存完整结果（游标只记录查询条件与分页位置）。
   - **每条结果保持精简**：标题、状态、最后活动时间、工作目录名、观测信息与成本估计、一句话摘要（≤200 字符）。原始请求全文、简报、历史用 `read` 按需读取。目标是一页约 1～2k token。（现状 `works` 每条带原始请求与任务内容各最多 1024 字符，一页最多 8 条，约 1.6 万字符。）
   - 已读过的页会留在协调对话历史中，翻页越多上下文越大。协调模型提示要求：优先用关键词搜索，而不是一页页往前翻；翻了 3 页仍未找到时，改用 `ask` 询问用户。
   - 暂不做语义（向量）检索；若评测显示关键词检索漏判明显，再考虑。
3. **仍然找不到时**（写入协调模型提示）：
   - 用户明确指向旧任务（"上次那个""之前的"）却找不到：用 `ask` 询问，选项为最可能的几个任务加"新建任务"，不猜测。
   - 用户没有指向旧任务：按新任务处理（`start`）。
4. **手动会话**：`find` 在符合原准入资格、尚未归入任务的手动会话中搜索（会话名、工作目录、最近活动），结果标注为"会话"，同样不受 32 个限制。派活后成为某任务的第 1 段，设置取其当时有效配置（见 3.5），此后通过任务查找，不再以独立会话候选重复出现。
5. **界面**：任务列表默认按"待你处理 → 执行中 → 排队中 → 最近结束"排序；已结束任务随时间下沉，可搜索。主侧栏中 WorkHub 创建的会话折叠为一组。
6. **旧 Session 自动归档：暂不做。**换窗续作需要读取旧段历史，归档前须先验证 `task_history` 能否读取已归档会话。有索引与折叠后，Session 增多主要只占用磁盘。出现磁盘或性能问题时，再增加"已结束超过 N 天的任务自动归档旧段"。

#### 3.10.1 关键词搜索流程

关键词由协调模型从用户的话中提取，可以是多个词，用空格分隔。

Host 侧（确定性）：

1. **规范化**：Unicode NFC、转小写、去掉首尾空白，按空格切成若干词；搜索字段与关键词使用一致规范化，原文和路径展示不被改写。
2. **逐词匹配**：
   - 词长 ≥ 3 个字符：用 FTS5 trigram 全文索引匹配。
   - 词长 < 3 个字符（如"登录""限流"）：trigram 不返回匹配，改用 LIKE 子串匹配。中文常见词多为两个字，这条路径会很常用。任务数量在数千级别时，LIKE 全表扫描耗时可以忽略。
3. **匹配范围与权重**：标题（最高）→ 原始请求、用户纠正 → 简报 → 会话名、工作目录名。
4. **过滤**：先限定工作目录等过滤范围；该范围同样用于下述 AND / OR 查询和无关键词回退。
5. **组合**：在限定范围内先要求所有词都命中（AND）；没有结果时，放宽为任一词命中（OR），并在结果中标注"已放宽"。
6. **合并去重**：按任务合并，同一任务的多段 Session 只出现一次；手动会话单独标注为"会话"。
7. **排序**：先按相关度（命中字段的权重、命中词数），再按最近活动时间。状态不参与排序，但每条结果都带状态。
8. **分页返回**：默认返回第一页（10 条精简结果）加游标；继续翻页沿用相同查询与过滤条件。
9. **仍无结果**：返回"未匹配"标记，同时附上相同过滤范围内不带关键词时的第一页。

查询参数化；FTS 特殊字符和 LIKE 通配符按字面搜索需求处理，文件名、路径及中文关键词不得因拼接语句而改变查询含义。

协调模型侧（写入提示）：

- 从结果中认出目标任务，必要时用 `read` 看详情，然后 `continue`。
- 没认出来时，可以换一组关键词再搜（例如同义词、文件名、目录名）。
- 翻了 3 页或重试后仍未找到，按第 3 条处理：用户明确指向旧任务就 `ask`，否则 `start` 新任务。

示例：用户说"把上次登录接口的限流测试再跑一遍"。

1. 模型调用 `find(query="登录 限流")`。
2. 两个词都只有 2 个字，走 LIKE；AND 组合命中 2 个任务。
3. 排第一的是标题为"登录接口补校验和限流"的任务（标题命中两个词），状态"已结束"，附带观测信息与成本估计。
4. 模型据此调用 `continue`，参考观测信息与成本估计自主选择复用或换窗。

| 协议 | 递增 epoch |

恢复约束：

- 不只验证解码与启动，还要覆盖升级前排队、活动执行、未决审批、旧依赖等待和半完成纠正的中间状态。
- 保留普通任务现有队列与恢复行为；停用旧协议不等于批量停止全部任务。旧授权不复活，失效交互不接受迟到回答，不重复执行工具或派发，不遗留并发名额与目录资源占用。
- 收尾沿用现有持久记录、停止与恢复路径；反复重启结果一致，不新建通用恢复框架，也不假造任务已完成。

## 7. 实施顺序

### 7.1 开工前

- 本 ADR 的源码核对基准为 `a7f6925`。开工前先运行 `git diff a7f6925..HEAD -- '*workhub*'` 以及相关 runtime-host、storage 文件，确认现状描述仍然成立；不成立时先更新本 ADR 再实施。
- 现有 WorkHub 文档（`docs/workhub-domain-language.md`、`docs/architecture/workhub-coordination-session-adr.md` 等）已过时，以源码与本 ADR 为准。

### 7.2 每个 PR 的约束

- 现有测试全部通过。删除功能时，连同其测试一起删除，并在 PR 描述中列出删除的测试。
- 不得通过放宽断言、延长超时、增加重试来让测试通过。
- 涉及持久数据的改动，必须同时完成第 6 节对应的兼容处理，并为"旧数据可读、Host 可启动、未完成操作可幂等收尾且不重复产生副作用"增加测试。
- 不修改 Maka 主界面中与 WorkHub 无关的部分。
- 协议有变化时递增 epoch。
- 同步更新或删除过时的 WorkHub 文档段落，不让文档与代码再次脱节。

### 7.3 步骤

每步独立 PR：

1. 删除 Jev 与预路由层；修正工具描述中关于意图检查的说法。必须同时处理第 6 节的 `jev` 策略字段、旧凭据的停用与读取兼容、`routingDecision`、用量调用类型，否则已有用户升级后 Host 可能因解码失败无法启动；不自动清除密钥。
2. Host 侧：任务设置快照与显式修改优先级、目录解析（沿用原权限 / 沙箱）、观测信息与成本估计、目标执行绑定及 stop 确认规则。
3. 任务权威字段与可重建索引（3.10）；工具改为 6 个任务工具；按 3.3 合并输入，保留状态语义与按需历史读取能力。
4. 删除纠正事务、候选快照、B、D、E 等待部分、F。注意：收件箱目前通过 `taskGrants.belongsToRoot` 找子代理请求，删除 D 前须把血缘证明抽成独立辅助函数。
5. 从现有记录临时拼装任务说明与历史入口；可选 worker 状态块，不新增交接总结调用。
6. 界面：任务标题、隐藏 Session 与 ID、任务视图内审批、主侧栏折叠、模型设置持久化。
7. 评测（第 1 步完成后即开始建设）。

### 7.4 实施者可自行决定的细节

- 任务索引表的字段细节、迁移编号、游标格式；
- 成本估计中各连接适用的 TTL、价格与用量字段映射（只用可核实来源，代理 / 自定义连接不能直接套原厂保证，取不到标"未知"）；
- 界面布局与文案细节；
- 代码组织与模块拆分。

超出以上范围、与本 ADR 冲突，或源码现状与本 ADR 不符时，先停下来向仓库所有者确认。

## 8. 验证

建立固定评测集，覆盖默认生产路径：

- sunrioa 在 #5745 报告的案例（误用 9 天前旧会话）；
- "新建 A → 无关的 B → 不带任务名的追问"，包括主对话最近主题与右栏预览不一致的场景；
- Jev 评测中的 12 条用例；
- 验收文档中的中文对话样本。

必要回归：

- 执行中直接纠正在下一次可消费边界进入同一轮，不打断工具、不偷偷另开一轮；排队补充不改变队列位置，取消 B 不影响 A。
- 忙碌、排队、停止中或存在未决审批时请求 `fresh`，明确拒绝且无新段副作用；空闲后 AI 可自主选择 reuse / fresh，复用仍可走现有压缩。
- 任务换段、请求重试或重启后，旧纠正 / 停止不误作用于新执行；自动通知不冒充用户新指令，多个停止不能通过拆分调用绕过确认。
- 修改 WorkHub 默认设置不改变旧任务；用户明确修改当前段设置后，新段继承其有效持久设置；单次 / 本轮许可不跨段。
- 同任务按需读回原始要求、后续纠正、工具调用与输出，排除同 Session 中其他任务内容；ai-sdk / executor 分别验证，缺失与不支持不能当空结果通过。
- 用户要求严格 JSON / 单行时不强制状态块；失败文件操作不显示为成功修改；没有进展信息不自动追加模型总结。
- 索引重建恢复任务、配置与阶段关系；中文短词、目录过滤后 AND / OR 回退、手动会话去重及重启后分页可用。
- 以实际旧格式及未完成中间状态覆盖第 6 节兼容；反复恢复不重复派发、不恢复旧授权、不遗留资源占用。
- 任务切换、各段完整历史与实时订阅不退化，审批仍绑定原请求；FIFO、并发、同目录串行及停止行为保留原回归。

行为和兼容测试可使用确定性夹具，并补真实模型、真实 coding 任务验证；夹具不能被当作供应商计费或模型路由质量的实测证据。

指标：

- 真实请求输入、输出、缓存读取 / 写入用量，以及已知连接价格下的估算费用；
- 续作判错比例；
- 换窗后用户决策与纠正的可读取性及实际遵守情况；
- 误停、重复派发、队列顺序变化与资源泄漏。

### 8.1 复用 / 压缩 / 换窗成本实测

始终由协调模型自主选择，不预置"缓存可能已冷则强制或默认换窗"规则。实测用于修正信息与推荐，不新增强制阈值。

测量方法：

1. 使用实际连接与模型，按有效窗口准备接近现有压缩条件的任务；不以固定 900k、1M 或固定比例替代模型配置。
2. 从等价任务与历史状态、隔离工作副本运行同一后续请求，对比复用（实际发生或未发生压缩）与换窗；覆盖不同缓存观测状态。避免顺序执行互相预热缓存后仍称为独立冷热对照。
3. 记录各请求实际用量和耗时，包括总结 / 修复调用、新段重新取证、输入与输出。按供应商字段定义归一化缓存与普通输入，避免双计；未知命中、价格或缓存状态明确标未知。
4. 当前连接价格可核实才换算费用，区分缓存读取 / 写入、普通输入和输出；换算结果不称为已核对的供应商账单。
5. 同时比较请求是否正确完成、用户纠正是否遵守、是否漏读必要证据；不能只看起步 token 较小就认定更优。

在实测前后都按 3.4 提供观测与有条件估计，由 AI 判断；单次执行只能观测被选方案的费用，不能伪称已知未选方案的真实成本。

## 9. 待验证的源码疑点

- 使用执行器（executor）的任务换窗后可能无法读取 `task_history`（`workhub-evidence-runtime.ts:532` 只允许 ai-sdk 后端）。需实测，新设计中需修复。
- `works` 分页可能重复返回同一任务（`workhub-work-index.ts:78-99`）。由 3.10 的任务索引取代。
- `task_history` 能否读取已归档会话，影响 3.10 第 6 条的后续决策。
- 压缩总结请求在真实连接上是否及如何命中主循环前缀缓存（主循环带系统提示和工具定义，总结请求不带），以及供应商缓存字段的准确含义；未验证前保持未知，不设统一命中价或换窗结论。
- 注释声称 `sessionId` 不暴露给模型，但 Desktop 原样返回候选（`workhub-runtime.ts:96-99`）。新工具设计中统一处理。
