## 1. 四条性质各自解锁什么

| 性质 | 解锁 |
|---|---|
| **校准** | 概率变成可运算的量 |
| **带外** | 判断你不该读、读不动、不许读的东西 |
| **便宜约 400 倍** | 本来没人会付钱做的决策 |
| **类型化** | 输出是程序值，不是待解析的文本 |

第四条单独看最无聊，但它是前三条能被安全依赖的前提 —— 没有"模型把 JSON
包在 markdown 里了"这种事，也就没有重试与容错的一整层。

## 2. 校准：概率变成可运算的量

这是最被低估的一条。多数系统把分类器的 confidence 当氛围看；校准意味着它是个**数**。

> **实测警告（2026-09-22）**：社区在 11,900 条标注 prompt 上测出 Jev 的 ECE 是
> **0.058**，Claude Haiku 是 **0.021** —— 与 TypeSafe 的宣称相反，Haiku 校准好约
> 三倍，而且 Jev 在 **0.5–0.9 区间不可靠**，那正是阈值所在的地带。
>
> 下面的数学方向都对，但**不要把它建在厂商声称的校准上**。用
> split conformal 在你自己的留出集上重新校准（现成工具 `jevcal`），
> 得到分布无关、有限样本的保证。见实施计划那份的
> [§4.5](./jev-decision-layer.zh-CN.md#45-校准验证自己校准不要信厂商的校准)。

### 2.1 阈值不用调，用算的

设 `C_act` 为误动作的代价、`C_miss` 为该动没动的代价，最优阈值是

```
p* = C_act / (C_act + C_miss)
```

不是凭感觉挑 0.7。**阈值从机器学习问题变成业务问题** —— 只需要知道两种错各自多贵。

### 2.2 弱信号能合成强决策

独立证据按 log-odds 相加：

```
logit(P) = logit(先验) + Σ [logit(Pᵢ) − logit(先验)]
```

先验 0.5 时：

| 输入 | 合并结果 |
|---|---|
| 三个各 0.60 | **0.77** |
| 三个各 0.70 | **0.93** |

三个各自平庸的检查合起来是个强结论。未校准的分数做不到 —— 把一堆不知道刻度的
数加权平均，得到的还是不知道刻度的数。

**独立性必须被工程化，不是默认成立的。** 三个子判断读同一个文件、用同一个模型、
同一套问法，它们共享盲区；朴素相加会严重高估。独立性要靠不同的**证据源**、
不同的**输入切片**来造，而不是同一输入的三种问法。拿不准时用保守合并
（取最大值，或给合并量一个收缩系数）。

### 2.3 能买到有保证的错误率

设阈值 `p` 以下全部升级给人或 frontier 模型，则**自动处理的那部分，
错误率在构造上有上界**。

你花的是**覆盖率**（多少比例需要升级），买到的是一个**可承诺的**质量下界。

**这是校准唯一能买到、而未校准系统给不了的东西。** 后者只能说"看起来不错"。

### 2.4 区分"有意义的分歧"和"噪声"

```
0.55 vs 0.45  →  两个都在说"我不知道"，是噪声，平均掉
0.95 vs 0.05  →  真冲突，它们看到的东西结构上不同，必须升级
```

用 `|logit(p₁) − logit(p₂)|` 量化分歧幅度。今天这两种情况拿到的都是
「我觉得没问题」对「我觉得可能有点问题」，分不开。

### 2.5 校准 ≠ 准确，这是最常被混淆的一点

| 模型 | 准确率 | 校准 |
|---|---|---|
| 在 50/50 问题上永远说 0.5 | 50% | **完美** |
| 90% 正确，但永远说 "0.99" | 90% | **很差** |

**第一个模型完美校准，且毫无用处。**

校准和**区分度**是两个独立的轴。校准让那个数**可信**，不让它**有信息量**。
所以验证时必须同时测校准曲线**和预测值的离散程度** —— 如果它在你的任务上
返回的全是 0.45–0.55，它是校准的，也是废的。

### 2.6 评估终于能有误差棒

LLM-as-judge 给一个点估计，偏差未知。校准的 judge 让你能在评估结果上
**放置信区间**。这是方法论升级，不是省钱。

## 3. 带外的极限用法

### 3.1 提示注入检测

> 这段工具输出里，是否包含指向 agent 的指令，试图改变它的行为？

**在内容进入上下文之前判断。** 今天所有注入防御都得先把攻击读进来才能识别它；
这个在结构上更好。

它和已实现的
[`redactContextCredentials`](./jev-decision-layer.zh-CN.md#方案-1grep-密钥判断)
是同一个 choke point、同一条性质、不同的问题 —— 合起来构成一道完整的
"内容进上下文前"的关卡。

#### 实测：比文献让人预期的好，但有前提

文献背景是悲观的：分类器方案在生产里 **5–15%** 的合法请求被误报；
DeBERTa-v3 在 JailbreakHub 上 FPR 高达 **0.96**；
EchoLeak（CVE-2025-32711）绕过了微软的 XPIA 分类器。

社区在 11,900 条标注 prompt 上的对照（`jev-injection-bench`）：

| 检测器 | 攻击检出 | 误报 | 过度防御 | ECE |
|---|---|---|---|---|
| Jev v2 | 77.6% | **0.3%** | 1.5% | 0.058 |
| Claude Haiku 4.5 | **86.7%** | 1.8% | 6.2% | **0.021** |
| PromptGuard-2 | 52.6% | 0.4% | 4.4% | 0.133 |
| PIGuard | 66.8% | 5.1% | 11.5% | 0.103 |

**0.3% 误报在那个文献背景下是个好数字**，且 PromptArmor（ICLR 2026）用现成 LLM
在 AgentDojo 上做到 <1% 双向错误，说明这条路走得通。

但要记住文献里那句话：

> **Every detector loses ground on a corpus its authors did not build.**

**0.3% 是别人语料上的数字。** 必须在你自己的内容分布上重测。作者自己列的
caveat 还有：措辞变化让结果偏移 28%，且完全没做对抗性测试。

已有实现：`jev-guard`（多 agent 的注入与危险动作守卫）、
`tripwire`（每个 LLM 响应跑七项检查，~100ms）。

### 3.2 判断读不动的东西

500MB 日志、5 万个文件的仓库、一年的工单。放不进上下文，但可以批量判断。

### 3.3 判断不许读的东西

受监管数据、另一个租户的数据、政策下的 PII。

**一个判断可以跨越数据本身不能跨越的边界** —— 你得到"这批记录里有没有异常"，
而没有任何一条记录进入 agent。

### 3.4 一条必须说清的限制

实施计划那份文档的 §2 写着「可以问'这一行是不是密钥'而那个密钥值从不进入
agent 上下文」。这句话是真的，但容易被读成"密钥不离开你的机器"。

**它离开了，只是去了 Jev 的服务方而不是进了 transcript。**

区别仍然实在：不进上下文意味着不进 transcript、不被后续每一轮重放、
不被你的模型厂商长期留存。但这是**换了一个暴露对象**，不是零暴露。
任何把 Jev 用于敏感数据的设计都要按这个前提评估。

## 4. 便宜到改变做法

### 4.1 仓库级审计

4000 个文件 × $0.0004 ≈ **$1.60**：

- 「这份文档还和代码对得上吗？」
- 「这个文件还有活路径引用吗？」
- 「这条注释描述的行为还存在吗？」

一杯咖啡的钱。今天这些事要么没人做，要么靠一个读不懂语义的 linter。

### 4.2 评估从"发布前仪式"变成"连续指标"

每一轮都打分"这轮做到用户要的了吗"，每次提交都跑。agent 质量变成一条实时曲线，
而不是一次性的门禁。

### 4.3 投机分支

判断比执行便宜约 400 倍，那就别再纠结生成哪个 —— 生成三个候选，打分，留一个。

**"思考该做什么"比"做三遍"还贵**，这个不等式一旦反转，工程习惯就该跟着变。

## 5. 四个展开的方向

### 5.1 agent 之间传递校准过的断言

**问题**：子 agent 返回文本，orchestrator 读完形成一个印象，没有任何算术可做。
三个子 agent 审同一段代码，两个说"没问题"一个说"有 bug"，今天只能靠感觉裁决。

**设计**：每个断言带校准概率，orchestrator 按 [§2.2](#22-弱信号能合成强决策)
合并、按 [§2.4](#24-区分有意义的分歧和噪声) 判分歧、按 [§2.3](#23-能买到有保证的错误率)
决定升级。

**证据何时足够 —— 最优停止**：不再"固定派三个审查员"，而是一直派到置信度越界：

```
持续追加验证，直到 P > 0.95 或 P < 0.05，上限 5 次
```

这是序贯概率比检验的实用形式。效果是**简单 case 花得少，难 case 花得多**，
而这正是想要的分配。

**真正的工作量在协议，不在模型**。子 agent 的返回需要多一个字段：

```
claims: [{ statement, probability, evidence_source }]
```

`evidence_source` 是为了让 orchestrator 判断独立性。这是个**契约变更**，
比接一个 API 难得多。

---

### 5.2 提前检测歧义

**问题的准确形式**：「含糊」不是正确的问题。大量请求含糊但无所谓 ——
因为任何合理读法产出的工作都一样。正确的问题是：

> **这个请求的两种合理读法，会导致实质不同的工作吗？**

「修一下登录的 bug」对*哪个* bug 是含糊的，但如果只有一个，那就不含糊。

**期望值算出来的结论很反直觉**。设返工代价约为多问一句的 20 倍，则

```
p* = 1 / 21 ≈ 0.048
```

**只要有约 5% 的返工概率就该问。** 这说明今天的 agent 问得**远远不够** ——
不是问多了烦人，是问少了浪费，两种错的代价差着一个数量级。

（修正项：若用户被问烦到弃用，`C_ask` 有个长尾，实际要测。但方向明确。）

**决定"问什么"比决定"问不问"重要得多**：

```
scope_unclear:     改动范围不清（一个文件还是整个模块）
target_unclear:    指代不清（有多个候选）
done_unclear:      完成标准不清
approach_unclear:  方向有多个合理选择，且代价差别大
none:              无实质歧义
```

「我有个问题」和「你是指 A 还是 B」的差别，就是烦人和有用的差别。

**会毁掉它的失效模式**：问用户已经回答过的事 —— 上一轮说过的、`CLAUDE.md` 里
写着的、项目约定里有的。state 必须包含常驻指令和近期历史，否则造出来的是一个
记性很差的同事，那比不问更糟。

**接在哪**：轮次开始前、第一次模型调用之前。此时 prompt 还不存在，零缓存代价。

### 5.3 复发错误检测

**问题**：「我们试过这个，炸了」这条知识活在没人读的复盘里、八个月前的 PR
评论里、或者某一个人的脑子里。

**为什么向量检索做不好**：embedding 按**表面相似**检索，而这里需要按**因果相似**
检索。两段文字可以用词完全不同却以同样方式失败，也可以用词高度重合却毫不相干。

```
"提到了同一个文件"    ← embedding 抓得到
"会撞上同一堵墙"      ← embedding 抓不到
```

#### 但也不需要检索 —— 实测语料根本装得下

对本仓库实测：

| 来源 | 数量 |
|---|---|
| revert 提交（4727 个提交中） | 22 |
| 已关闭的 bug issue | 251 |
| 未关闭的 bug issue | 99 |
| 用户拒绝/纠正过的轮次 | 数十 |

**总计约 400 条。** 每条压成约 200 字符（做了什么 → 怎么失败的）：

```
400 × 200 = 80,000 字符
Jev state 上限 = 107,500 字符
```

装得下，还剩两成余量。成本约 **$0.0013**，延迟 **250ms**，需要的基础设施 **无**。

#### 一条一般性的教训

> RAG 的两段式架构，是对**"读很贵"**这个成本结构的回应。
> Jev 把"读"变便宜了约 400 倍，那个前提没了，**检索就成了过早优化**。

交叉点在哪：

| 语料规模 | 做法 | 成本 | 延迟 |
|---|---|---|---|
| ≤ 500 | 一次调用 | $0.0013 | 250ms |
| 2,000 | 4 次并行 | $0.005 | <1s |
| 10,000 | 20 次并行 | $0.026 | 几秒 |
| 100,000 | 200 次 | $0.26 | 开始需要设计 |

**单个仓库永远到不了需要检索的规模。** 跨组织、跨年份的事故库才可能。

#### 最小实现

```
.jev/failure-corpus.jsonl          一个文件，每行一条
scripts/build-failure-corpus.mjs   从 git log + gh issue 生成
```

**连摘要都不用做** —— issue 标题本身就是摘要：

```
bug(runtime): output-free streams closed before response.completed bypass bounded recovery
```

90 个字符，把失败机制说清楚了。语料条目 = issue 标题 + 修复提交的 subject +
涉及的文件路径。全程零 LLM 参与，纯脚本。执行计划前一次调用，整个文件当 state。

加起来约一百行。没有向量库、没有 embedding 厂商、没有索引新鲜度问题、
没有分块逻辑。

**额外的好处**：语料是 git 里的纯文本文件 —— 可读、可审、可 diff。
你能打开它看见系统"知道"什么，能手工删掉过时的一条，能在 PR 里 review 新增的。
向量库这三件事一件都做不到。

#### 诚实的边界

**它只抓复发**，对新错误完全无用 —— 而新错误是大多数。

价值完全取决于失败是否真的重复。在一个特定代码库里重复得很厉害
（同样的三四个架构陷阱，每个新人踩一遍），所以**范围收得越窄越值钱**：
「在这个代码库里，有没有人试过 X 然后回滚了」比泛化的失败知识高一个量级。

### 5.4 diff 分诊

**问题**：50 个文件的 PR 被**均匀的**注意力审查 —— 也就是递减的注意力。
重要的那处在第 34 个文件，到那儿已经没人在看了。

**criteria 要拆开原因，不能只问"危险吗"**：

```
security_surface:  改了认证、权限、输入校验、加密
silent_failure:    移除或弱化了错误路径 / 断言 / 校验
contract_change:   改了公共接口、wire 格式、或持久化形状
concurrency:       涉及并发、锁、异步顺序
business_logic:    改了影响结果正确性的核心逻辑
mechanical:        重命名、格式化、依赖升级、生成物
test_only:         只动测试
```

**最后两类是主要收益。** 典型 PR 里 60–80% 的 hunk 是机械改动或纯测试，
把它们移出注意力预算就拿到大半价值 —— 而这恰恰是 linter 做不到的判断：
**重命名和逻辑修改在 differ 眼里长得一模一样。**

**第二个维度才让它从"显然"变成"好"**：只按风险排序不够，你要的是
`P(评审者能在这里发现问题)`。

```
优先级 = P(有缺陷) × P(人能读出来 | 有缺陷)
```

一个 500 行的生成文件风险不低但**可审性**极差；一个 3 行的认证判断改动可审性极高。
第二项才是把"危险清单"变成"值得你花时间的清单"的东西。

**呈现方式和打分同样重要**。不要重排 diff（评审者需要文件结构做锚），
而是在顶部给摘要：

```
5 处需要注意：3 处契约变更、1 处移除了错误路径、1 处触及认证
（另有 41 处机械改动已折叠）
```

带跳转链接；机械类默认折叠但**显示计数**，让人知道它们存在且被看过。

**三个边界**：

- **缺失的改动它看不见。** 缺陷常常是这个 PR *没做*的事 —— 没加的校验、
  没更新的调用点。逐 hunk 打分对此完全无能。
- **跨 hunk 的交互它看不见。** A 单独没问题、B 单独没问题，合起来死锁。
  缓解：第二遍用整个 diff 作 state，专门问交互。
- **校准会随仓库漂移。** 什么算 "business logic" 每个项目不一样，
  需要 per-repo 的样本集。

**成本**：50 个 hunk 一次批量调用，约 $0.002。

### 5.5 5.1 和 5.4 是同一件事的两端

diff 分诊是分诊，校准断言是级联 —— 接起来就是完整的东西：

```
Jev 给 50 个 hunk 打分
  ├─ 41 个机械      → 不看
  ├─ 6 个中等 (0.2–0.8) → 派子 agent 深审，返回校准断言
  └─ 3 个高危      → 直接给人
                    ↓
       子 agent 的断言按 log-odds 合并
                    ↓
       合并后仍不确定的 → 升级给人
```

**你为一个可承诺的错误率付钱，付的是覆盖率** —— 多少比例必须升级。
这正是 [§2.3](#23-能买到有保证的错误率) 说的那件事。

## 6. 几个更大胆的

**验证的经济学翻转了。** 今天不验证，是因为验证几乎和做一样贵。便宜 400 倍之后，
**验证一切** —— 每一句声明、每一步、每一个输出。agent 从"被信任"变成"可核查"。
前面那些具体应用都是这一条的特例。

**校准置信度作为面向用户的契约。** 一个给每句话附上真实概率的 agent，配一个设置：
「只告诉我你有 90% 把握的事，其余标出来」。今天 agent 要么无意义地对冲、
要么错误地断言；一个刻度真实的置信度改变的是人机信任关系。

**学出来的打断策略。** 「这个用户会希望被问这件事吗？」—— 拿他自己过去的
接受/拒绝行为做校准。今天每个 agent 关于"何时打断人类"的规则都是硬编码的。

**复发错误检测的反向用法。** 同一份语料也能回答「这个改动是否修复了某个已知失败」，
即自动的 issue 关联。

## 7. 诚实的边界

**它不做开放推理。** 它从你给的集合里选。**质量上限是 criteria 设计**，
不是模型能力。

**烂 criteria 给你校准得很好的垃圾。** 校准是关于"你问的那个问题"的，
不是"你想问的那个问题"。这个失效模式很隐蔽，因为它带着一个自信的数字。

**它是一个依赖。** 第二个厂商、第二个故障面、**第二条数据出境路径**
（见 [§3.4](#34-一条必须说清的限制)）。

不过这一条可能正在失效：调研当时（2026-09-22）四天内已出现至少十个本地/开源
复刻，其中 `von` 号称 sub-15ms、非自回归、可本地直接替换；`openjev` 在家用
3090 上跑；`decider`（Qwen3.5-2B 微调）输出带校准概率的类型化决策。
**对密钥与注入这两个用途，本地替代值得在设计早期就评估。**

**它是个过滤器，不是个更好的判断者。** 六份独立评测指向同一个模式：

> Jev 赢在成本、延迟和误报率；在原始准确率上打平或输，
> 而且在校准上也常常输给 Claude Haiku。

所以别把它接在需要判断质量的地方，要接在昂贵步骤的前面。那份重排序评测的结论
（Jev 与 BM25 单独都不赢，**fusion 赢**）是同一件事的另一种说法。
汇总见实施计划那份的
[§8.2](./jev-decision-layer.zh-CN.md#82-六份独立评测)。

**不可逆动作上不能用。** 校准的"80% 置信 = 80% 正确"反过来读是**五次错一次**；
删除、推送、转账、授予写权限，这个数字在任何实际阈值上都不够。
详见实施计划那份的 §3.3。
